Context-Preserving Managed Install Repair
=========================================

Purpose
-------
Define a first-class recovery operation for rebuilding a damaged project-local
Codex package install without deleting the project's Codex context or history.

Scope
-----
This specification covers the `codex-wrangler --repair
/absolute/path/to/project-root` command, including target selection, managed
ownership proof, exact-version recovery, cleanup boundaries, and operator
documentation.

Requirements
------------
1. Explicit absolute target
   `--repair` must take the project root as its own mandatory value. The value
   must be an absolute path to an existing directory above the managed
   `bin/`, `.local/codex/`, and `.local/codex-home/` paths. Repair must reject a
   relative value and any additional positional project root so a spare
   `codex-wrangler` executable can safely repair a different checkout without
   depending on its current working directory.
2. Exclusive recovery operation
   Repair must reject operation flags and install-selection options that could
   change its meaning, including `--upgrade`, `--update`, `--inspect`,
   `--selftest`, `--uninstall`, `--channel`, `--version`, `--skip-install`,
   `--repair-install`, permission-default changes, and managed path
   overrides. Diagnostic npm timeout and log-level options, `--dry-run`, and
   `--force` may retain their ordinary meanings. `--shared-home` or
   `--isolated-home` is permitted only as recovery authority when no
   surviving managed record retains HOME mode; it may not change a surviving
   recorded choice.
3. Managed ownership proof
   Before removing any artifact, repair must prove that the target contains an
   existing `codex-wrangler`-managed install. Strong proof consists of valid
   current-schema managed metadata whose recorded project root and every
   canonical managed path match the resolved target layout, a validated active
   slot completion record, or the managed local package manifest. Copied,
   stale, or layout-mismatched metadata alone must not authorize repair. If no
   source can be validated, repair must stop without cleanup or generated-file
   writes.
4. Exact-version recovery
   Repair must infer the exact installed Codex version from surviving managed
   metadata, lockfile, package manifest, or installed Codex package manifest.
   Selector values such as `latest`, `stable`, `beta`, or `alpha` are not
   exact recovery evidence. Conflicting exact versions must stop repair for
   operator review. When no exact version survives, repair must stop rather
   than implicitly upgrading to a current registry version.
   A valid completion record selected by a valid active pointer is
   authoritative over stale root projections and the rollback slot. When the
   pointer or selected completion record is invalid, no active slot is
   authoritative: repair must aggregate root, incomplete selected-slot, and
   all completed-slot evidence, then refuse any disagreement. Every weak
   manifest or lockfile source must be a regular non-link file reached only
   through non-link ancestors inside its claimed npm prefix.
   HOME mode and reasonable-permissions state use the same active-first
   authority rule. Without a valid selected completion record, all surviving
   root and completed-slot Boolean values must agree. If HOME mode is absent
   from every authority, repair must require exactly one explicit
   `--shared-home` or `--isolated-home` choice. Conflicting explicit and
   surviving choices must stop repair. If reasonable-permissions evidence is
   absent, repair must conservatively disable that launcher default.
5. Automatic bounded cleanup
   A proven repair must reinstall the inferred exact version into a unique
   candidate outside both fixed slots, validate it, and only then reversibly
   rename it into inactive `.local/codex/slots/a` or `slots/b`. Cleanup remains
   limited to unique candidate/cache scratch data after normal path safety
   checks. The active slot, rollback slot, and legacy root runtime must remain
   untouched until the candidate succeeds and is atomically promoted. A repair
   of one malformed pointer or incomplete selected slot must quarantine rather
   than delete any fixed-slot tree displaced after validation.
6. Protected context and history
   Repair must never delete or recreate `.local/codex-home`, the legacy
   `.codex-home` name, `.codex`, `.agents`, unrelated
   `.local` contents, project source, ad hoc backups, or any context,
   authentication, sessions, memories, history, logs, goals, or other
   assistant state outside the bounded managed npm cleanup paths. In
   particular, repair must report an absent isolated HOME and stop rather than
   creating a replacement that could silently sever history; this check must
   happen before candidate installation. Complete ignore coverage may be
   atomically published before candidate work. Existing managed launcher,
   README, and metadata may be regenerated only after the replacement candidate
   passes validation.
   Configuration must reject any removable package tree or generated output
   that contains, equals, or descends into those reserved context roots (and
   repository `.git` data) before repair performs any mutation.
7. Standalone execution
   Recovery logic must derive all target paths from the explicit project root
   and target-side managed records. It must not assume that the running
   `codex-wrangler` checkout is the target project or use target-local Python
   modules or the damaged target launcher.
8. Verification
   After npm installation, repair must apply the same native-payload and
   `codex --version` verification used by normal installation. A failed
   verification must report failure without touching protected context.

Validation
----------
- Parser tests must cover a missing repair value, a relative repair value,
  and an extra positional project root.
- Configuration tests must cover exact-version inference, no surviving exact
  version, conflicting exact versions, active-first HOME authority, concordant
  fallback aggregation, missing-mode explicit recovery, conflicting HOME
  overrides, and unsafe flag combinations.
- Operation tests must prove ownership before cleanup, automatic cleanup and
  exact-version reinstall, and preservation of context/history sentinels.
- Rendering tests must document the absolute-path standalone recovery command
  in both repository and generated local guidance.
