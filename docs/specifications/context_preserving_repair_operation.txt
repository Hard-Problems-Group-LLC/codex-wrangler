Context-Preserving Managed Install Repair
=========================================

Purpose
-------
Define a first-class recovery operation for rebuilding a damaged project-local
Codex package install without deleting the project's Codex context or history.

Scope
-----
This specification covers the `codex-wrangler --repair
/absolute/path/to/project-root` command, including target selection, managed
ownership proof, exact-version recovery, cleanup boundaries, and operator
documentation.

Requirements
------------
1. Explicit absolute target
   `--repair` must take the project root as its own mandatory value. The value
   must be an absolute path to an existing directory above the managed
   `bin/`, `.codex-local/`, and `.codex-home/` paths. Repair must reject a
   relative value and any additional positional project root so a spare
   `codex-wrangler` executable can safely repair a different checkout without
   depending on its current working directory.
2. Exclusive recovery operation
   Repair must reject operation flags and install-selection options that could
   change its meaning, including `--upgrade`, `--update`, `--inspect`,
   `--selftest`, `--uninstall`, `--channel`, `--version`, `--skip-install`,
   `--repair-install`, HOME-mode changes, permission-default changes, and
   managed path overrides. Diagnostic npm timeout and log-level options,
   `--dry-run`, and `--force` may retain their ordinary meanings.
3. Managed ownership proof
   Before removing any artifact, repair must prove that the target contains an
   existing `codex-wrangler`-managed install. Strong proof consists of valid
   current-schema managed metadata whose recorded project root and every
   canonical managed path match the resolved target layout, or the managed
   local package manifest. Copied, stale, or layout-mismatched metadata alone
   must not authorize repair. If neither source can be validated, repair must
   stop without cleanup or generated-file writes.
4. Exact-version recovery
   Repair must infer the exact installed Codex version from surviving managed
   metadata, lockfile, package manifest, or installed Codex package manifest.
   Selector values such as `latest`, `stable`, `beta`, or `alpha` are not
   exact recovery evidence. Conflicting exact versions must stop repair for
   operator review. When no exact version survives, repair must stop rather
   than implicitly upgrading to a current registry version.
5. Automatic bounded cleanup
   A proven repair must automatically apply the existing managed npm repair
   cleanup before reinstalling the inferred exact version. Cleanup remains
   limited to `.codex-local/node_modules`, `.codex-local/package-lock.json`,
   `.codex-local/.npm-cache/_npx`, and
   `.codex-local/.npm-cache/_cacache/tmp` after the normal path safety checks.
6. Protected context and history
   Repair must never delete or recreate `.codex-home`, `.codex`, `.agents`,
   `.local`, project source, ad hoc backups, or any context, authentication,
   sessions, memories, history, logs, goals, or other assistant state stored
   outside the bounded managed npm cleanup paths. Existing managed launcher,
   README, metadata, and ignore records may be regenerated only after
   ownership and version inference succeed.
7. Standalone execution
   Recovery logic must derive all target paths from the explicit project root
   and target-side managed records. It must not assume that the running
   `codex-wrangler` checkout is the target project or use target-local Python
   modules or the damaged target launcher.
8. Verification
   After npm installation, repair must apply the same native-payload and
   `codex --version` verification used by normal installation. A failed
   verification must report failure without touching protected context.

Validation
----------
- Parser tests must cover a missing repair value, a relative repair value,
  and an extra positional project root.
- Configuration tests must cover exact-version inference, no surviving exact
  version, conflicting exact versions, and unsafe flag combinations.
- Operation tests must prove ownership before cleanup, automatic cleanup and
  exact-version reinstall, and preservation of context/history sentinels.
- Rendering tests must document the absolute-path standalone recovery command
  in both repository and generated local guidance.
